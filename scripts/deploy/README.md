# Aéza · Контроль продлений — systemd на Ubuntu

Шаблоны рассчитаны на один Ubuntu-хост с локальным диском и HTTPS reverse proxy. Контейнеры не нужны. Они запускают внутреннюю панель ручного учёта; подключение к биллингу или управление серверами Aéza здесь не добавляется.

## Размещение

| Путь | Владелец и доступ | Содержимое |
|---|---|---|
| `/opt/aeza-renewals/current` | `root:root`, сервису только чтение и исполнение | Релиз: `backend/`, собранный `frontend/dist/`, зависимости `.venv/` |
| `/etc/aeza-renewals` | `root:root`, `0700` | Каталог секретной конфигурации |
| `/etc/aeza-renewals/environment` | `root:root`, `0600` | Заполненный `EnvironmentFile` |
| `/var/lib/aeza-renewals` | `aeza-renewals:aeza-renewals`, `0700` | SQLite, WAL и постоянные состояния доставки/опроса |

Пользователь `aeza-renewals` — отдельная системная учётная запись без входа. Его можно создать шаблоном `aeza-renewals.sysusers.conf`, установленным в `/usr/lib/sysusers.d/aeza-renewals.conf`, и командой `systemd-sysusers /usr/lib/sysusers.d/aeza-renewals.conf`. Эта команда выполняется оператором с правами root.

Исходники, все родительские каталоги, Python и `.venv` должны быть читаемы/исполнимы этим пользователем, но недоступны ему для записи. Каталоги релиза обычно имеют `0755`, обычные файлы `0644`, исполняемые файлы `0755`. Не выдавайте сервису владение релизом. В релизе не должно быть `.env`: приложение получает значения через systemd и всё равно проверяет наличие локального `.env`; существующий недоступный файл может помешать запуску. Внешний `/etc/aeza-renewals/environment` читает systemd до перехода к непривилегированному пользователю.

`StateDirectory=aeza-renewals` создаёт постоянный каталог данных с владельцем сервиса. Все три процесса используют один файл из абсолютного `DATABASE_PATH`. Системные ограничения оставляют код и зависимости только для чтения, а приватный `/tmp` доступен каждому процессу отдельно.

## Подготовка и запуск оператором

1. Разместите готовый релиз в `/opt/aeza-renewals/current`. Установите Python 3.12+, создайте `.venv` именно на Ubuntu и установите `requirements.txt`. Windows `.venv` переносить нельзя. В релизе уже должен находиться собранный `frontend/dist`; установка пакетов и сборка выполняются до запуска сервиса.
2. Подготовьте `/etc/aeza-renewals/environment` по `environment.example`. Пустые секреты намеренно не запускают приложение. Передайте реальные значения через защищённый канал, не через аргументы командной строки и не в логи. Укажите точный HTTPS `APP_ORIGIN`, `COOKIE_SECURE=true` и абсолютный путь базы. Не выполняйте `source` для этого файла.
3. Установите три `.service` в `/etc/systemd/system/` с владельцем `root:root`, режимом `0644`. Проверьте на целевом Ubuntu:

```bash
sudo systemd-analyze verify /etc/systemd/system/aeza-renewals-{api,worker,bot}.service
sudo systemctl daemon-reload
```

4. Для новой базы сначала запустите только API. Он создаст таблицы и администратора из окружения:

```bash
sudo systemctl enable --now aeza-renewals-api.service
```

Демо seed запускается отдельно и только по решению оператора для новой среды. Пример одноразового запуска под тем же пользователем с тем же закрытым файлом окружения:

```bash
sudo systemd-run --unit=aeza-renewals-seed --wait --pipe --collect \
  --property=User=aeza-renewals --property=Group=aeza-renewals \
  --property=WorkingDirectory=/opt/aeza-renewals/current \
  --property=EnvironmentFile=/etc/aeza-renewals/environment \
  --property=UMask=0077 --setenv=PYTHONUTF8=1 --setenv=PYTHONDONTWRITEBYTECODE=1 \
  /opt/aeza-renewals/current/.venv/bin/python -m backend.seed
```

Этот seed не является автоматическим шагом запуска. Его суммы демонстрационные; существующая финансовая история не заменяется. Не удаляйте действующую базу ради демоданных. Для резервной копии остановите процессы или используйте согласованный SQLite backup API; при активном WAL нельзя копировать только основной `.db`.

5. После проверки HTTPS/proxy и состава ожидающих напоминаний включите фоновые процессы:

```bash
sudo systemctl enable --now aeza-renewals-worker.service aeza-renewals-bot.service
sudo systemctl status aeza-renewals-api.service aeza-renewals-worker.service aeza-renewals-bot.service
```

Содержимое environment и токены не выводите при диагностике. Журнал процесса доступен оператору через `journalctl -u aeza-renewals-bot.service` и аналогичные имена. `Type=simple` означает запущенный процесс, а не готовность HTTP API: проверка `/api/v1/health` выполняется отдельно.

## Proxy и завершение

API слушает только `127.0.0.1:8000`. Uvicorn доверяет forwarded-заголовкам только от `127.0.0.1`. Локальный HTTPS proxy должен перезаписывать `X-Forwarded-For` фактическим адресом клиента и `X-Forwarded-Proto` фактической схемой; передавать им без проверки произвольные значения клиента нельзя. Если proxy подключается по другому адресу, измените доверенный адрес осознанно. Не открывайте Uvicorn непосредственно наружу. Пока HTTPS не настроен, production cookie с `Secure` не работает по HTTP.

Все три сервиса останавливаются `SIGTERM`, с пределом `45s`. У API ожидание завершения запросов ограничено `30s`. Worker сохраняет один HTTP-клиент и завершает текущую Telegram-попытку перед выходом: connect `5s` с одним повтором только до отправки, write `5s`, read `15s`, pool `5s` (обычный бюджет попытки около `30s`; это отдельные сетевые таймауты, а не жёсткий общий deadline). Ошибки чтения/записи не повторяются. Polling-бот проверяет остановку после long poll (до `20s`, клиентский timeout `30s`) и во время повторных ожиданий. На Ubuntu `--stop-file` не требуется. При превышении `45s` systemd может завершить процесс принудительно: неопределённые доставки останутся для проверки, а ответы бота с уже сохранённым offset автоматически не повторятся.

`Restart=on-failure` повторяет аварийный запуск с паузой `5s`; после десяти быстрых сбоев за пять минут применяется ограничение частоты. После исправления конфигурации оператор может выполнить `systemctl reset-failed` и запустить сервис снова. Установленный Telegram webhook бот не удаляет: перед polling его совместимость проверяется отдельно.

До переноса одного токена на новый хост остановите старые worker и poller. SQLite lease защищает только процессы с одной базой, а не разные серверы. При переносе состояния сохраняйте outbox вместе с его финансовыми периодами, offset — вместе с областью того же токена. В новую финансовую демобазу нельзя переносить outbox со старыми идентификаторами периодов.
