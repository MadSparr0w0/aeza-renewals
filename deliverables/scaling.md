# Загрузка данных частями

Сайт не скачивает все месячные периоды, определения платежей и участников после входа. Разделы запрашивают только нужные данные; уход с раздела и изменение поиска отменяют устаревшие запросы. Поиск запускается после короткой паузы ввода.

## Контракт страниц

`GET /api/v1/payment-occurrences/page?month=2026-10&limit=30&offset=0`

Ответ содержит `items`, `total`, `limit`, `offset`, `has_more`. Обычный размер — 30, максимум API — 100. `offset` неотрицателен. Сервер применяет права пользователя до подсчёта и выборки. Данные разных команд не попадают в общий `total`.

Фильтры: `month`, `day`, `currency`, `status`, `search`; сортировки `due_date`, `name`, `amount`, направление `descending`. Вторичный порядок по ID делает порядок однозначным при одинаковых значениях. Суммы сортируются внутри валюты. Поиск кириллицы использует Unicode casefold, значения передаются параметрами SQL.

Участники, отдельные администраторы, действия и очередь используют `/users/page`, `/admins/page`, `/activity/page`, `/reminders/page`. Список администраторов доступен только конфигурационному администратору и не даёт доступа к чужим финансам. Старые совместимые списки ограничены 100 строками. В личном кабинете бота также используется ограниченная SQL-выборка.

## Итоги и календарь

`/payments/summary` считает суммы и количество в SQL по всему доступному набору; эти показатели не выводятся из текущих 30 строк. `/payments/calendar` возвращает агрегаты максимум по 31 дню, суммы отдельно по валютам. Список выбранного дня загружается отдельной страницей.

Условия одной серии для редактирования запрашиваются по ID. Поиск ответственного на сайте не загружает всех участников. Выгрузка CSV явно относится к текущей странице.

Для дат, состояний, владельцев и следующего создаваемого периода добавлены индексы. Материализация читает только серии, у которых подошёл следующий период, пакетами по 128 определений; уже созданные серии не обновляются на каждом чтении. Чтение страниц не пересоздаёт очередь уведомлений.

## Воспроизвести проверку

```powershell
.\.venv\Scripts\python.exe scripts/benchmark_pagination.py --rows 50000 --runs 10
```

Скрипт создаёт отдельную временную SQLite с 50 000 синтетических записей, проверяет первую и глубокую страницы по 30 строк, полноту итогов и календаря. Рабочая база и сеть не используются. В локальном Windows-прогоне 25.10.2026 медианы составили примерно 20 мс для первой страницы и 33 мс для глубокой, ответы — около 10 КБ.

Это последовательный тест ASGI+SQLite на конкретной машине; он не является измерением внешней сети, конкурентной нагрузки или гарантией SLA. При параллельном изменении списка offset-страницы могут сдвигаться: после изменения данных следует обновить список. SQLite остаётся локальной базой одного хоста; горизонтальное масштабирование потребует отдельного решения.
