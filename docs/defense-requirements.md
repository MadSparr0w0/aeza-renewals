# Требования к защите и доказательства

Источник исходных требований — выданный кейс Invoice Keeper, 18 страниц. Последующие пояснения заказчика отдельно изменили продуктовую модель. Здесь не смешиваются текст PDF, согласованная новая спецификация и фактические результаты проверки 25 октября 2026.

## 1. Что требует исходный PDF

| Страницы | Требование |
|---|---|
| 1-2 | Администратор вносит регулярные расходы, пользователи контролируют общий список и оплаты; Telegram напоминает за три дня |
| 3 | Две роли, RUB/USD/EUR, суммы отдельно, конвертация не требуется |
| 4 | Название, сумма, валюта, ближайший срок, периодичность; достаточно ежемесячной; единый TZ; последний день короткого месяца |
| 4-5 | У каждого периода свой срок/статус, история сохраняется; просрочка старого не блокирует новый |
| 5 | Фактическая дата, отмена с очисткой, просрочка со следующего дня; исправление даты не меняет срок |
| 6 | Веб-авторизация, полный список полей, admin из .env, права проверяются и через API |
| 7 | Telegram с названием/суммой/валютой/датой; без дублей; позднее добавление напоминает сразу |
| 8 | Бот сам проверяет сроки; оплаченные и прекращённые не напоминают; повторная проверка не дублирует |
| 9 | Admin управляет регулярными платежами и обычными пользователями; обычный пользователь смотрит общий список, меняет оплату/дату; admin не меняется через панель |
| 10 | Запуск по README, закрытый доступ, права, независимые периоды и напоминания — условия приёмки |
| 11 | Статусы/просрочка, валюты, сохранение после рестарта, история при удалении, исходники/инструкция/.env.example/демоданные |

| 15 | Семь действий вживую, от входа admin до следующего независимого периода |
| 16 | Девять необязательных возможностей; они не заменяют обязательную часть |
| 17 | Польза, корректность, удобство; стек и архитектуру выбирает команда |

## 2. Последующее уточнение заказчика

- Универсальные ежемесячные расходы под брендом Aéza, без ограничения услугами провайдера.
- Один экземпляр — одна команда и одна общая корпоративная Telegram-группа.
- User создаёт и полностью обслуживает **только собственные** расходы; admin видит и обслуживает все, может создать за участника.
- Admin добавляет пользователя с паролем либо выдаёт одноразовое приглашение на 72 часа. По приглашению пароль задаёт участник; успешное принятие выдаёт fresh session.
- Обычный участник меняет пароль по текущему и новому; затем все сессии отзываются и нужен новый вход. Env-admin через API неизменяем.
- Telegram только уведомляет группу: владелец, платёж, сумма, валюта, срок. Нет финансовых команд и отметки оплаты.
- Привязка: web-код на 10 минут, команда Telegram-admin, проверка кандидата и отдельное web-подтверждение.
- Legacy-личный чат не подключается автоматически. Получатель фиксируется в outbox.
- Удаление участника передаёт его серии env-admin с сохранением истории.

Общий пользовательский список из PDF заменён личной областью. Право создания сотрудником расширяет исходную матрицу. Это **явные изменения заказчика**, а не дословное выполнение старых формулировок. Остальные обязательные правила и маршруты сохраняются.

## 3. Семь живых действий со страницы 15

| ID | Исходный шаг | Новый демонстрационный пример |
|---|---|---|
| D1 | Войти администратором | Вход admin, видимость всех расходов |
| D2 | Добавить регулярный платёж | «Аренда · демонстрация», 1500 RUB, близкий срок, владелец A |
| D3 | Получить напоминание в Telegram | Новое сообщение с владельцем в подтверждённой группе |
| D4 | Войти пользователем и отметить оплату | A отмечает **тот же** принадлежащий ему период |
| D5 | Показать просроченный платёж | Подготовленный собственный период A |
| D6 | Исправить фактическую дату | Поздняя дата → день срока, просрочка стала 0 |
| D7 | Показать следующий период | Отдельный статус следующего месяца той же серии |

До D1 готовятся участник A, собственный просроченный пример, работающий worker и реальная подтверждённая группа. Admin обязан назначить owner A на D2, иначе личный доступ A на D4 правильно скроет запись.

После D7 отдельно показать создание сотрудником, изоляцию A/B, приглашение/смену пароля и привязку группы. Эти функции не подменяют D1-D7. Скриншот или запись — явно обозначенный резерв, а не живой D3.

25 октября фактическая группа «InKeep» подключена кодом и web-confirm; Bot API подтвердил две новые отправки. Прочтение каждым не заявляется. Это доказательство работы внешнего пути, но семь действий выступления всё равно нужно показать вживую.

## 7. Честные формулировки и подготовка

Не обещать абсолютную exactly-once доставку или прочтение всеми. Sent означает ответ Bot API; unknown не повторяется вслепую. Реальная оплата выполняется вне модуля, отметка ручная. Одна команда/одна группа — явный масштаб версии.

Перед защитой подключить тестовую группу, получить новое сообщение, пройти D1-D7, подготовить прямую проверку чужого ID и административного API. Для доказательства запрета больше не использовать POST создания собственного расхода user: теперь он разрешён. Проверять управление участниками/группой и чужие записи.

Публичный экран не содержит паролей, invitation token, cookie, SSH-доступа и реальных финансовых данных. Источники реализации: README, docs/architecture.md, docs/security.md, docs/telegram.md, backend/app.py, backend/invitations.py, backend/telegram_connections.py. Факты релиза — docs/qa.md.
