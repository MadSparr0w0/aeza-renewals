# Развёртывание «Aéza · Контроль продлений»

Публичный тестовый стенд: **[https://138.124.14.93/](https://138.124.14.93/)**. Модуль развёрнут нативно через systemd; фактические результаты проверки приведены в [qa.md](qa.md), а размещение, units и команды эксплуатации — в [scripts/deploy/README.md](../scripts/deploy/README.md).

## Подтверждённое развёртывание

Сервер использует Ubuntu 26.04, Python 3.14.4 и nginx 1.28.3. Для публичного IP успешно выпущен короткоживущий TLS-сертификат через Certbot 5.8, установленный в отдельном виртуальном окружении. Пробное продление сертификата в режиме dry-run прошло успешно. Внешняя проверка HTTPS, HSTS и перенаправления HTTP с кодом `308` прошла. После финального обновления `.cache/verify-remote.py` повторно подтвердил также RBAC, CSRF и Origin.

Три systemd-сервиса API, worker и bot активны и работают от непривилегированного пользователя `aeza-renewals`. Код принадлежит root и доступен сервису только для чтения/исполнения. Файл окружения принадлежит root с режимом `0600`; каталог данных имеет `0700`, SQLite-файл — `0600`. Весь серверный набор из **130 тестов прошёл за 11.62 секунды**, с одним известным предупреждением Starlette о тестовом клиенте. После изменения эмодзи бота и профиля отдельно прошли 63 целевых теста Telegram/polling/profile; этот прогон не прибавляется к числу уникальных тестов полного набора.

Развёрнута новая синтетическая база с шестью сериями Aéza и условными ценами. Прежняя локальная база сохранена в приватной резервной копии. На этапе переноса прежнего бота offset и receipts были сохранены, старый outbox не переносился: его идентификаторы относились к другой финансовой базе. Затем рабочая конфигурация переключена на `@aezainkeep_bot`; новый токен использует отдельную область offset/lease. Подтверждены три доставки демонапоминаний новым ботом и ответы на команды. После перезапуска доставки не повторились. Обновлённый профиль, семь команд и присланный аватар опубликованы; все семь команд проверены обратным чтением Bot API.

Полированная версия сайта и обновлённый бот успешно перенесены на сервер; все три службы активны. Актуальные frontend-ресурсы: `index-CW5-7-ui.js` и `index-DbInrObd.css`. Все акценты интерфейса оранжевые `#E97C35`; повторяющиеся информационные блоки убраны. Срок аренды сервера по предоставленному скриншоту — **26.10.2026 18:00**; до этой даты нужно сохранить приватную копию данных вне стенда.

## Что переносится

Публичная поставка содержит код, готовый `frontend/dist`, OpenAPI, инструкции, лицензии и безопасные бренд-материалы. Имя каталога `invoice-keeper` сохранено для совместимости. На сервере приложение по-прежнему состоит из API, worker напоминаний и обработчика Telegram-команд с одной SQLite на локальном постоянном диске.

Отдельно и только по защищённому каналу переносятся рабочий `.env` и, при миграции действующего экземпляра, согласованная копия базы. В публичный архив не входят:

- SSH-пароли, приватные ключи, токен бота и рабочие пароли модуля;
- локальный `.env`, база и её приватные резервные копии;
- исходные скриншоты с доступами к тестовому серверу и терминалы с секретами;
- реальные финансовые экспорты и персональные данные.

Для отчёта используются снимки интерфейса приложения, без секретов. Условные демоцены не являются тарифами Aéza.

## Подготовка окружения

1. Подготовить тестовый сервер, проверить доступ оператора, свободное место и срок действия аренды. До его окончания сохранить приватную резервную копию вне этого сервера.
2. Разместить проверенную поставку в каталоге приложения. Готовую сборку frontend можно использовать без Node.js на сервере; при изменении интерфейса сначала пересобрать её по README.
3. Для нового независимого экземпляра создать `.env` через `scripts/init_env.py`. Для переноса действующего экземпляра использовать его проверенные настройки и базу. Секреты не передавать в аргументах команд и не копировать в файлы исходников.
4. Задать `APP_ORIGIN` равным фактическому HTTPS-origin стенда без пути и завершающего `/`, `COOKIE_SECURE=true`, нужный `TIMEZONE` и путь к постоянной базе. `APP_ALLOWED_ORIGINS` в серверной среде оставлять пустым, если дополнительные origin не нужны.
5. Ограничить чтение файла окружения оператором и процессами развёртывания. На Linux для обычного env-файла использовать права `0600`; предоставить контейнерам доступ к данным через штатный том.

Учётная запись администратора модуля задаётся `ADMIN_USERNAME` и `ADMIN_PASSWORD_HASH`; это отдельная конфигурация от SSH и кабинета Aéza. Пароли провайдера, SSO и токены его биллинга модулю не требуются. Интеграция с услугами остаётся в режиме ручного учёта.

## Перенос действующего бота и данных

Для текущего `@aezainkeep_bot` перед переносом остановить локальные API, worker и bot. Создать согласованную копию всей SQLite, включая историю, outbox и `telegram_pollers`/`telegram_updates`. При активном WAL нельзя произвольно копировать только основной `.db`: используйте SQLite backup API или остановку всех процессов перед копированием.

Восстановить базу в постоянном каталоге данных или контейнерном томе и проверить права доступа. Outbox сохраняет подтверждённые/неопределённые доставки, offset — обработанные Telegram-обновления. Новая пустая база с повторным seed не сохраняет эти состояния и может заново создать демонстрационные напоминания. При осознанном создании новой финансовой демобазы нельзя переносить старый outbox с несоответствующими идентификаторами периодов; перенос offset/receipts того же токена выполняется отдельно.

Для одного токена оставлять один командный poller. Блокировка общей SQLite не координирует разные базы на локальном компьютере и сервере. Передача роли удалённому экземпляру выполняется после остановки локального. Токен и числовой ID чата в публичном отчёте не указываются.

## Запуск и внешний доступ

На текущем стенде используются `aeza-renewals-api.service`, `aeza-renewals-worker.service` и `aeza-renewals-bot.service`. Код размещён в `/opt/aeza-renewals/current`, закрытый EnvironmentFile — в `/etc/aeza-renewals/environment`, постоянные данные — в `/var/lib/aeza-renewals`. Точная подготовка и настройки служб описаны в [инструкции systemd](../scripts/deploy/README.md).

Docker Compose остаётся альтернативой: он запускает `api`, `worker` и `bot` из одного образа с постоянным томом `invoice-data`. Команды приведены в README. Серверная проверка текущего стенда относится к systemd, а не к контейнерному запуску. Для новой базы демонстрационный seed выполняется явно; при переносе действующей базы заново наполнять её не требуется.

API по умолчанию доступен только на `127.0.0.1:8000`. Снаружи приложение публикуется через reverse proxy с TLS. Публично доступен HTTPS proxy; файл базы и внутренний порт API не открываются. В настройках cookie включён `Secure`, а origin соответствует адресу, которым пользуется браузер. HTTPS и сертификат нужно проверить с клиентского компьютера.

При нативном запуске использовать отдельные процессы из README и штатный менеджер служб сервера для перезапуска и остановки. `scripts/run.ps1` предназначен для локального Windows-запуска. Контейнерные worker и bot имеют время для мягкой остановки; не используйте принудительное завершение как обычный способ обновления.

После изменения закрытого EnvironmentFile текущие systemd-сервисы перезапускает оператор:

```bash
sudo systemctl restart aeza-renewals-api.service aeza-renewals-worker.service aeza-renewals-bot.service
sudo systemctl status aeza-renewals-api.service aeza-renewals-worker.service aeza-renewals-bot.service
```

Для альтернативного Compose-развёртывания после изменения env-файла сервисы пересоздаются:

```bash
docker compose up -d --force-recreate api worker bot
docker compose logs -f api worker bot
```

Публикация имени, описаний, команд и аватара Telegram выполняется отдельно через `scripts/configure_telegram.py`, как описано в `telegram.md`. Она не рассылает сообщения. Непрочитанные задания напоминаний обрабатывает worker независимо от настройки профиля.

Текущий бот — `@aezainkeep_bot`. Его идентичность подтверждена `getMe`, а доступ к выбранному личному чату — `getChat`; пустой ответ `getUpdates` не препятствует уже проверенной привязке. Рабочие конфигурации переключены на нового бота. Для публикации профиля используется `--expected-bot aezainkeep_bot` и неизменённый пользовательский `assets/telegram/avatar.jpg`. Проверка или оформление профиля не подтверждают доставку серверных напоминаний.

Для связи сервера с Telegram оператор применил временное сопоставление `api.telegram.org` с доступным официальным адресом: обычный DNS-вариант `149.154.166.110` был недоступен по TCP, а `149.154.167.220` ответил HTTP `302` при сохранённом hostname и действительном TLS-сертификате. Временный маршрут успешно применён. Проверка сертификата не отключалась. После применения маршрута подтверждены **три демодоставки `sendMessage` со статусом `sent`**, без ошибок; после перезапуска они не повторились. Это подтверждение реальной доставки, а не только доступности сетевого пути.

## Проверка релиза

Перед передачей адреса проверить:

1. HTTPS, точный origin, защищённый cookie; без входа данные и Swagger возвращают отказ.
2. Вход администратора и обычного пользователя; административные изменения недоступны обычному пользователю и через прямой API.
3. Просмотр периодов, валютные итоги, отметку/отмену оплаты и сохранение истории после перезапуска.
4. Изменение будущих условий без изменения текущих/прошлых/оплаченных периодов; отказ `409` при несозданной истории или отправляемом напоминании.
5. Единственный Telegram-poller, команды и кнопки в разрешённом чате, сохранённые состояния отправок без повторной рассылки.
6. Локальную загрузку фирменного знака/шрифтов, мобильный интерфейс и русскую документацию API.

Результаты фиксируются только после фактической проверки. Токены, ID личного чата, пароли сервера и рабочие cookie в отчёт не переносятся.

## Обновление и восстановление

Перед заменой версии остановить все три процесса и сохранить приватный снимок базы. После обновления запускать приложение с прежним постоянным томом. `docker compose down` сохраняет данные; вариант с `-v` удаляет том и не подходит для обычного обновления.

При восстановлении сверить outbox и offset до запуска Telegram-процессов. Старый снимок может содержать задания, уже доставленные после его создания: такие доставки сначала нужно проверить, иначе восстановление способно вернуть их в очередь. Неопределённые результаты `unknown` автоматически не повторяются. Приватные резервные копии хранить отдельно от публичного ZIP и ограничить доступ к ним.
