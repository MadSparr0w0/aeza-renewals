# Приёмка Aéza Регулярные платежи

Матрица командной версии 25 октября 2026. Исходный источник - выданный кейс Invoice Keeper, 18 страниц. Последующее пояснение заказчика отдельно меняет модель доступа и использования Telegram. Эта таблица не выдаёт новую трактовку за текст PDF. Проведённые проверки отделены от будущего выступления.

## Уточнения заказчика после PDF

| ID | Уточнение | Что нужно доказать |
|---|---|---|
| C1 | Одна команда и одна общая корпоративная Telegram-группа | В интерфейсе и конфигурации нет обещания нескольких организаций/групп |
| C2 | User видит и полностью обслуживает только свои расходы; admin все | Два пользователя не читают и не меняют записи друг друга, включая прямые ID, итоги и историю |
| C3 | Сотрудник сам создаёт расход; admin может создать за участника | User создаёт только себе; admin задаёт существующего owner; подмена owner отклоняется |
| C4 | Admin добавляет участника с паролем либо приглашением | Оба пути работают; произвольная самостоятельная регистрация отсутствует |
| C5 | Одноразовое приглашение на 72 часа, имя/логин задаёт admin | Участник задаёт пароль, получает fresh session; истёкшая/отозванная/использованная ссылка не принимается |
| C6 | Участник меняет свой пароль по текущему и новому | После успеха все его сессии отозваны, требуется повторный вход; env-admin через API не меняется |
| C7 | Telegram только уведомляет общую группу | Нет финансовых команд и подтверждения оплаты; владелец, платёж, сумма, валюта и срок видны группе |
| C8 | Код группы на 10 минут, проверка Telegram-admin, затем web-подтверждение | Код или /start не включают доставку; личный legacy-чат не наследуется |
| C9 | Получатель фиксируется в outbox | Замена текущей настройки не перенаправляет старое задание; отключение отменяет pending/retry |
| C10 | Удаление участника сохраняет историю, передавая серии env-admin | Все серии, включая архивные, сменили owner в одной транзакции; ID/условия/периоды/отметки сохранены |

C2 - сознательное изменение общего пользовательского списка из PDF. C3 расширяет исходное право создания, отнесённое в PDF к администратору. Их нельзя описывать как дословные исходные требования. Они принимаются по последующему подтверждённому пояснению заказчика.

## Обязательный API и обновлённый доступ

Все пути имеют префикс `/api/v1`.

| Метод и путь | Доступ новой версии |
|---|---|
| POST /auth/login | Без сессии, ограничение попыток |
| GET /auth/me | Авторизованный |
| POST /auth/logout | Авторизованный + CSRF |
| GET /recurring-payments | User свои; admin все |
| POST /recurring-payments | User себе; admin себе/участнику; CSRF |
| DELETE /recurring-payments/{id} | Владелец или admin + CSRF |
| GET /payment-occurrences | User свои; admin все |
| GET /payment-occurrences/{id} | Владелец или admin |
| PATCH /payment-occurrences/{id} | Владелец или admin + CSRF |
| GET /payments/summary | Только разрешённые владельцы |
| GET /users | Admin |
| POST /users | Admin + CSRF |
| PATCH /users/{id} | Admin + CSRF, обычные участники |
| DELETE /users/{id} | Admin + CSRF, передача серий env-admin |
| GET /docs | Авторизованный |

Дополнительные контракты: `PATCH /recurring-payments/{id}`, `/invitations`, `/invitations/inspect`, `/invitations/accept`, `/auth/password` и `/telegram/connection`. Они не заменяют обязательные методы. Точные пути и поля приведены в текущих OpenAPI и project-guide.md.

## Сценарии новой проверки

1. Обычный пользователь A создаёт собственную серию и обслуживает её полностью.
2. Пользователь B не видит серию A в списках, истории, итогах и по прямому ID; не меняет и не прекращает её.
3. Admin видит обе области и создаёт серию на A. Переданный user чужой `owner_id` не даёт права создать за B.
4. Пройти создание с паролем и приглашением; повтор/отзыв/истечение ссылки, валидацию пароля и невозможность назначить роль.
5. После принятия приглашения доступна новая сессия; после смены пароля прежние сессии не действуют.
6. Неадминистратор Telegram-группы, личный чат и неверный/истёкший код не подключают получателя. Кандидат без web-confirm не получает уведомлений.
7. Подтверждённая группа получает сообщение с владельцем и четырьмя полями PDF; финансовых команд нет.
8. Отключение отменяет pending/retry, sent/unknown сохраняются. Group → supergroup требует повторной привязки.
9. Проверить штатные повторы worker, неопределённый исход и сохранение адреса назначения задания.
10. Проверить короткий месяц, три валюты, независимые периоды, оплату/отмену/исправление даты, сохранение после рестарта.
11. При удалении участника проверить передачу всех его серий env-admin без потери истории.
12. Воспроизвести запуск по README, Swagger/OpenAPI, упаковку без секретов и семь живых действий.
