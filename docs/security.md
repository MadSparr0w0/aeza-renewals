# Безопасность модуля «Aéza · Контроль продлений»

## Что защищаем

Система хранит финансовые названия и суммы, сроки, историю оплат, пользователей и сессии. Секреты — пароль администратора, ключ подписи/сессий и токен Telegram. Доверенные компоненты: сервер приложения, worker напоминаний, обработчик Telegram-команд, локальный файл базы и оператор окружения. Браузер, HTTP-ввод и содержимое Telegram-обновлений находятся за границей доверия. Подключённый Telegram-чат получает право просмотра финансовых данных без веб-сессии.

Учётные записи принадлежат этому модулю. Пароль от кабинета Aéza для входа в модуль не нужен и не запрашивается. Ссылка «Кабинет Aéza» ведёт на официальный внешний сайт с отдельной авторизацией; сессия модуля туда не переносится. Интеграция работает в режиме ручного учёта: статусы не являются подтверждением списания, реального баланса или состояния услуги. Изменение или прекращение учёта не меняет инфраструктуру у провайдера.

## Контроли

| Риск | Контроль |
|---|---|
| Доступ к данным без входа | Серверная проверка сессии для API и документации; интерфейс показывает вход до загрузки финансовых данных |
| Данные Telegram уходят в чужой чат | Точное совпадение ID с `TELEGRAM_CHAT_ID` для команд и кнопок; неподходящие обновления игнорируются |
| Подмена параметров кнопки | Проверка чата исходного сообщения и допустимых значений раздела, месяца и страницы; кнопки только для просмотра |
| Повторная обработка Telegram-обновлений | Сохранение offset до ответа и один poller на токен в общей SQLite; ограничение частоты обращений |
| Обычный пользователь вызывает административный API | Проверка роли сервером на каждом изменении регулярных платежей и пользователей; ответ `403` |
| Изменение администратора через API | Администратор определяется только окружением; создание администратора и управление им через CRUD запрещены |
| Утечка паролей | Соль и адаптивный хеш; пароль не возвращается в API и не пишется в логи |
| Угон сессии | Случайный серверный токен, ограниченный срок жизни, `HttpOnly`, `SameSite`; `Secure` при HTTPS; завершение сессии при выходе |
| CSRF | Токен на изменяющих запросах и проверка origin; один origin для frontend и API |
| Подбор пароля | Ограничение повторных попыток входа; одинаковая ошибка для неверного логина и пароля |
| SQL injection | Параметризованные SQL-запросы и серверная валидация |
| XSS | React экранирует текст, пользовательские названия не интерпретируются как HTML; защитные HTTP-заголовки |
| Подмена суммы/валюты/даты | Сервер проверяет ограничения, деньги хранятся целыми минимальными единицами, принимаются только RUB/USD/EUR |
| Изменение истории при новых условиях | Администратор меняет только неоплаченные будущие периоды со следующего месяца; устаревший указатель генерации и отправляемое напоминание дают атомарный отказ `409` |
| Дубли напоминаний | Уникальный outbox на период и атомарный захват; неопределённая доставка не повторяется вслепую |
| Чтение секретов через frontend | `.env` читает backend; секреты не используют `VITE_` и не входят в bundle |
| Утечка файлов проекта | FastAPI отдаёт только сборку frontend, а не корневой каталог, `.env` или базу |
| Запуск с привилегиями | Docker запускается от отдельного пользователя, без Linux capabilities и записи в корневую ФС |

## `.env` и администратор

В репозитории находится только `.env.example` с пустыми секретами. Локальный `.env`, данные SQLite и сборочные зависимости исключены из Git и Docker build context. Секреты создаются локально при инициализации; опубликованные пароли по умолчанию не используются. В рабочей среде можно передать те же значения через систему секретов инфраструктуры вместо файла.

Администратор — отдельная конфигурационная учётная запись. Смена его логина или пароля выполняется оператором через окружение и перезапуск сервисов. Обычные пользователи создаются администратором; передача полей роли не должна давать возможность повышения привилегий. Удаление/изменение пользователя должно отзывать применимые сессии.

Часовой пояс, cookie, origin и Telegram задаются централизованно. Пример для локального HTTP сознательно использует cookie без `Secure`; для публичной среды обязательны HTTPS и `COOKIE_SECURE=true`. Поле `VITE_*` никогда не подходит для токена бота или серверного пароля: Vite публикует такие значения в клиентском JavaScript.

## Telegram

Токен остаётся в серверном окружении; его используют worker напоминаний и обработчик команд. Чат получает название, сумму, валюту, срок и сведения о статусе. Разметку сообщений формирует сервер, а пользовательские названия экранируются. HTTPS-запрос ограничен таймаутом. Токен находится в URL Telegram API, поэтому полный URL/объект запроса нельзя писать в общие логи или трассировки.

Для команд разрешён только чат с точным ID из `TELEGRAM_CHAT_ID`. Проверяется реальный чат сообщения или callback, а не username и не ID из пользовательских аргументов. В личной переписке у callback дополнительно сверяется отправитель. Inline callback без контекста чата не допускается. Неавторизованные сообщения и кнопки не получают финансовых данных. Параметры пагинации валидируются; чрезмерная частота обращений ограничивается.

Подключение группы означает разрешение просмотра для её участников. Индивидуальные роли веб-пользователей внутри Telegram не проверяются. Оператор отвечает за выбор чата и его состав. Чат не получает полномочий администратора приложения.

Telegram-команды и кнопки предназначены для просмотра. Оплата подтверждается в веб-панели с проверенной сессией и CSRF; через бота нельзя менять сумму, срок, пользователей, статус или дату оплаты. Обработка будущего месяца может создать его периоды по действующим правилам, но не подтверждает их оплату.

Offset сохраняется в SQLite до сетевого ответа, а lease ограничивает запуск одним обработчиком токена в общей базе. После сбоя уже принятому обновлению не отправляется автоматический повторный ответ. Это уменьшает риск повторной обработки ценой возможного отсутствия ответа; пользователь может повторить команду. Блокировка не защищает от другого приложения с тем же токеном и отдельной базой. Запуск нескольких poller или параллельное чтение `getUpdates` вручную не поддерживаются.

Служебный `scripts/configure_telegram.py` использует токен только при отдельном применении профиля. Перед изменениями он проверяет ожидаемый username и подключённый чат. Публично задаются только команды `/start` и `/help`, полный список — в области разрешённого чата; фактический доступ к данным всё равно проверяет runtime. Режим `--dry-run` завершает проверку локальных файлов до чтения `.env` и сетевых запросов. Применение профиля не отправляет сообщения и не изменяет права веб-пользователей.

При переносе на сервер сохраняются outbox и offset. Локальный обработчик того же токена останавливается перед запуском удалённого: блокировка одной SQLite не координирует независимые базы на двух хостах. Нельзя заново наполнить пустую базу теми же демоплатежами и считать прежние доставки сохранёнными.

## Публичное развёртывание

1. Разместить API за reverse proxy с TLS и ограничением размеров запросов.
2. Включить `Secure` для cookie и указать точный origin приложения.
3. Закрыть прямой доступ к базе и порту приложения извне; доступен только proxy.
4. Выдать файлу окружения доступ только оператору, ограничить доступ к резервным копиям.
5. Отслеживать ошибки worker и обработчика команд, неопределённые доставки и неудачные входы; не логировать пароли, session/CSRF-токены, токен бота или полные Telegram-обновления.
6. Обновлять зависимости и образы; хранить резервные копии и проверять восстановление.

SSH-доступ к тестовому серверу отделён от учётных записей веб-модуля. Пароли сервера, рабочий `.env`, ключи и резервная копия базы передаются по защищённому каналу и хранятся отдельно от исходников. Исходные скриншоты с доступами, терминалы с секретами и реальные финансовые экспорты не включаются в `qa/screenshots` или публичный архив. Подробная последовательность переноса приведена в `deployment.md`.

## Ограничения

Текущая поставка предназначена для небольшой команды на одном хосте. Это не платёжный процессинг: банковские карты и платёжные реквизиты не хранятся. Нет MFA, распределённого rate limiter, восстановления пароля по email или управления инфраструктурными секретами. Защита от распределённого перебора и DDoS для публичной среды дополняется на reverse proxy/edge.

Cookie `SameSite` сам по себе не заменяет CSRF-проверку. Изменение финансового статуса пользователем допустимо по модели кейса; оно не должно позволять изменять сумму, срок или чужую учётную запись. Логирование не заменяет серверную проверку прав.
