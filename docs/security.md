# Безопасность Aéza Регулярные платежи

Модель безопасности командной версии 25 октября 2026. Новые права, приглашения и привязка группы проверены текущим набором 154 тестов; фактическое развёртывание и доставка описаны в qa.md.

## Две области видимости

В веб-панели обычный пользователь видит и полностью обслуживает только свои расходы, периоды и итоги. Администратор видит все записи команды и управляет участниками. Во всех запросах источник полномочий - серверная сессия и проверенный владелец; `owner_id` из тела запроса не даёт права присвоить себе чужую запись.

В одной подключённой корпоративной Telegram-группе участникам видны имя владельца, название расхода, сумма, валюта и срок. Это сознательно согласованная общая область уведомлений. Личная область веб-панели не означает конфиденциальность деталей, уже опубликованных в группе. Бот не принимает финансовых команд и не выдаёт списки по запросу участников.

Модуль не хранит банковские карты и не исполняет платежи. Записи и ручные отметки не являются подтверждением банковского списания. Биллинг или пароль кабинета Aéza для работы не нужны.

## Контроли нового контракта

| Риск | Контроль и проверка |
|---|---|
| Доступ к данным без входа | Сессия обязательна для финансового API, Swagger и OpenAPI |
| Участник читает чужой расход по ID | Владелец проверяется для одиночных записей и истории; не только фильтр UI |
| Участник видит чужие суммы в итогах | Сервер ограничивает series, occurrences и summary своим владельцем |
| Подмена владельца в POST | User создаёт только себе; admin может указать существующего участника |
| Изменение/прекращение чужой серии | Сервер проверяет владельца либо роль admin для каждого действия |
| Управление участниками от user | Административные маршруты отклоняют обычную роль |
| Повышение роли через JSON | Модели не принимают произвольное назначение admin; env-admin неизменяем |
| Утечка приглашения | Одноразовый токен на 72 часа, хеш на сервере, исходная ссылка выдаётся только при создании |
| Повторное принятие приглашения | Проверка срока/состояния и атомарное использование; логин/имя назначает admin |
| Захват группы одним знанием кода | Код на 10 минут, проверка Telegram-группы и статуса отправителя, затем отдельное подтверждение web-admin |
| Наследование старого личного чата | Legacy-чат не подключается автоматически |
| Подмена получателя старого задания | Конкретный chat ID зафиксирован в outbox, а не читается динамически перед отправкой |
| Дубли доставки | Постоянное задание, атомарный захват, `sent` без повтора, `unknown` без слепого повторения |
| Смена пароля оставляет доступ | Текущий пароль обязателен, после успеха все сессии обычного пользователя отзываются |
| Удаление участника уничтожает историю | Серии переходят env-admin в одной транзакции; история сохраняется, доступ участника прекращается |

Методы групп находятся под /api/v1/telegram/connection. Отключение отменяет pending/retry, сохраняет sent/unknown и offset. При активной отправке требуется дождаться её завершения; миграция в supergroup требует новой привязки.

## Пароли и сессии

Пароли хешируются с солью через scrypt. Серверная сессия использует случайный токен в cookie; в базе хранится его HMAC, а не открытый токен. Cookie имеет `HttpOnly`, `SameSite=Strict`, при публичном HTTPS - `Secure`. Срок задаётся конфигурацией, по умолчанию 12 часов.

После входа изменяющим запросам нужны та же сессия и `X-CSRF-Token`. Для браузерных запросов проверяется допустимый Origin; открытые inspect/accept приглашений требуют точный Origin по контракту. `SameSite` не заменяет CSRF. Ошибка входа не раскрывает существование логина; попытки ограничиваются по IP и паре IP/логин.

Принятие приглашения и смена пароля - разные действия:

- При успешном принятии приглашения пользователь выбирает пароль и получает новую сессию. Назначенные администратором имя и логин не заменяются публичным запросом. Использованная ссылка больше не действует.
- При самостоятельной смене пароля обычный пользователь передаёт текущий и новый пароль. Все его сессии, включая текущую, отзываются; нужен новый вход.
- Создание обычного пользователя администратором с заданным паролем остаётся отдельной возможностью. Такой участник затем может сменить свой пароль самостоятельно.
- Конфигурационный администратор через API не меняется. Оператор меняет его логин/хеш в закрытом окружении и перезапускает сервисы.

Ссылка приглашения содержит секрет. Её нельзя помещать в слайды, общую группу или публичные логи. Фрагмент URL `#invite=TOKEN` сам по себе не отправляется HTTP-серверу; frontend читает его и передаёт токен только целевому API. Frontend не должен сохранять токен в историю приложения или публичные сообщения. Открытые обращения ограничиваются по IP и токену; ошибки не раскрывают секретную ссылку.

## Финансовые запросы

Проверка владельца выполняется до выдачи или изменения записи и не заменяется полем `can_manage` в ответе. User не может обойти ограничение с помощью ID чужого периода, `owner_id`, фильтра месяца, поиска или экспорта. CSV строится только из разрешённого списка. Admin может обслуживать все расходы; доступ к пользователям, приглашениям и привязке группы остаётся административным.

Входные данные валидируются сервером: неизвестные поля, суммы, валюты, даты и длины строк. Деньги считаются целыми минимальными единицами. SQL параметризован. React экранирует текст, имена в HTML Telegram тоже экранируются. Журнал не должен содержать пароли, invitation token, session/CSRF token или полный Bot API URL.

## Подключение и доставка Telegram

Знание кода подключения даёт возможность предъявить кандидата, но не включить рассылку. Отправитель `/connect@aezainkeep_bot CODE` должен быть администратором фактической Telegram-группы. Web-admin затем видит найденную группу и подтверждает её. Имя чата и username пользователя не заменяют числовой chat ID и проверку статуса через Telegram.

В финальную группу уходят уведомления с согласованными деталями владельца. Оператор и администратор команды должны учитывать состав группы: удаление участника из веб-приложения само по себе не удаляет его из Telegram-группы и не стирает опубликованные сообщения.

Токен бота хранится только на сервере. API URL Telegram содержит токен, поэтому нельзя логировать полный URL или объект запроса. При переносе токена на другой хост старый poller и worker останавливаются; lease одной базы не координирует другой экземпляр.

`sent` означает успешный ответ Bot API, а не прочтение всеми. Неопределённый результат получает `unknown` без автоматического повтора, потому что сообщение могло дойти. Отменить уже переданное Telegram сообщение гарантированно нельзя. Бот не предоставляет кнопки «Оплачено» или финансовых меню.

## Окружение и публикация

В репозитории находится только `.env.example` без секретов. Рабочий `.env`, SQLite, резервные копии, SSH-доступ и финансовые экспорты исключены из публичного архива. Секреты не передаются в `VITE_*` и не участвуют в frontend-сборке.

Публичная среда использует HTTPS reverse proxy, точный `APP_ORIGIN`, `COOKIE_SECURE=true`, закрытый внутренний порт API и ограниченный доступ к базе. Код работает от непривилегированного пользователя, окружение и резервные копии доступны только оператору. Приложение не шифрует SQLite на диске: защита диска - задача инфраструктуры.

Один хост и одна команда - граница этой версии. Нет MFA, самостоятельной регистрации без приглашения, восстановления по email, распределённого rate limiter или платёжного процессинга. Журналирование и красивый интерфейс не заменяют серверную проверку владельца.
